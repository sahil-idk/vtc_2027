1What is a "cell", exactly?

Everything in this script is organized around the idea of a "cell" — one physical antenna sector that the vehicle can connect to. But the dataset doesn't give us a single, ready-made "cell ID" column we can just group on. Instead, a cell is defined, in the script, as the unique combination of five columns:

CELL_ID_COLS = ["operator", "PCell_MCC", "PCell_MNC", "PCell_TAC", "PCell_Cell_Identity"]

Two rows are considered "the same cell" if and only if all five of these values match exactly. Here's what each one contributes, and why all five are needed together rather than just one:

ColumnWhat it isWhy it's needed in the key
operatorWhich of the two mobile network operators (1 or 2) this row belongs to The two operators run completely separate physical networks. A cell identity number from Operator 1's network has no relationship to a cell identity number from Operator 2's — they're different towers even if the raw number happened to match.
PCell_MCCMobile Country Code (262 = Germany, in this dataset) Standard 3GPP identifier for which country's network this is. Included for completeness and correctness — in this single-country dataset it's constant, but the definition should be correct in general.
PCell_MNCMobile Network Code (identifies the specific operator within that country) Confirms which of the two operators' networks issued this cell identity, independent of the separate operator column.
PCell_TACTracking Area Code — an administrative grouping of nearby cells the network uses for mobility management Cell Identity numbers are only guaranteed unique within a Tracking Area. The same numeric Cell Identity value can, in principle, be reused in a different Tracking Area for a physically different cell. Without TAC, two unrelated towers could get merged into one "cell" by mistake.
PCell_Cell_IdentityThe actual cell/sector identifier within its Tracking Area This is the specific antenna sector the vehicle was connected to — the thing whose physical position we're actually trying to estimate.
In code This definition is what makes the grouping step work: df_clean.groupby(CELL_ID_COLS) later in the script. Pandas treats every unique combination of these five values as its own group — that group is "a cell" for the rest of the script.

3Step 1 — loading the dataset and the Gate-1 clean filter

df = pd.read_csv(CLEANED_CSV, low_memory=False)
# 207,434 rows total

clean_mask = ~df[RANGE_FLAG_COLS].any(axis=1)
df_clean = df[clean_mask].dropna(subset=CELL_ID_COLS[1:] + ["Latitude", "Longitude", "PCell_RSRP_max"])

Before any grouping happens, every single row in the dataset — all 207,434 of them — is checked against two things:

  1. Gate-1 cleanliness: none of FLAG_range_PCell_RSRP_max, FLAG_range_PCell_RSRQ_max, FLAG_range_PCell_RSSI_max, or FLAG_range_PCell_SNR_1 may be True. If any of them are, the row is excluded from tower estimation entirely — there's no point building a position estimate out of a measurement we already know is physically implausible.
  2. Completeness: the row must actually have a value for every column the rest of the script needs — MCC, MNC, TAC, Cell Identity, Latitude, Longitude, and RSRP. A row missing any of these can't be grouped or weighted.

Applied to the real dataset, this leaves 192,296 of the original 207,434 rows eligible to continue. Our example row has all four flags False and every required field present, so:

passes Gate-1 clean filter → continues to grouping

The loop then processes one cell — one bucket — at a time. Our example row is one member of the bucket keyed by (1, 262, 1, 1492, 26947072), which contains 5,083 rows in total (assuming all of them independently pass the same Gate-1 filter — in practice a few might not, but the vast majority do for this particular busy cell).

5Step 3 — the minimum-data gate

if len(group) < MIN_ROWS_FOR_ESTIMATION:  # MIN_ROWS_FOR_ESTIMATION = 20
    n_towers_insufficient += 1
    continue  # skip this cell entirely -- no estimate is produced

Before doing anything else with a cell's group of rows, the script checks whether there's even enough data to bother. Fewer than 20 rows for a cell, and the script gives up on it outright — no position is guessed, the cell is simply absent from the final tower list. This happened to 58 cells in the real run.

Our example cell has 5,083 rows — nowhere near the 20-row floor — so:

5,083 ≥ 20 → proceeds to the split

6Step 4 — the deterministic per-cell split

This is the step that avoids the circularity problem: every row in the group is randomly assigned to one of two roles, localization or validation, and — critically — the split is computed before any position estimate exists.

seed = stable_seed_for_cell(cell_key)
rng = np.random.RandomState(seed)
is_localization = rng.rand(len(group)) < LOCALIZATION_FRACTION  # 0.6

localization_rows = group[is_localization]
validation_rows = group[~is_localization]

How the seed is generated

def stable_seed_for_cell(cell_key: tuple) -> int:
    key_str = "_".join(str(x) for x in cell_key)
    return int(hashlib.md5(key_str.encode()).hexdigest(), 16) % (2**31)

For our example cell, cell_key = (1, 262, 1, 1492, 26947072) becomes the string "1_262_1_1492_26947072", which gets MD5-hashed into a long hexadecimal number, then reduced modulo 2³¹ into a plain integer seed. This number is completely determined by the cell's own identity — the same cell always produces the same seed, every single time the script runs, regardless of which order the cells happen to be processed in, or how many other rows exist elsewhere in the dataset.

How the seed turns into an actual split

rng.rand(len(group)) uses that seed to generate exactly one random number between 0 and 1 for every row in the group — 5,083 numbers for our example cell, all reproducible from the same seed. Each row's number is then compared against LOCALIZATION_FRACTION = 0.6: a number below 0.6 sends that row to localization_rows; 0.6 or above sends it to validation_rows. Since each row gets an independent random draw, roughly 60% of the 5,083 rows land in localization and roughly 40% in validation — not exactly 60/40, since it's random, but close, especially with this many rows.

Why this specific design A per-cell seed (rather than one seed for the whole dataset) means adding or removing OTHER cells' data never changes this cell's split. And because the split happens strictly BEFORE the position estimate is computed in Step 6, no row can ever end up used both to build the estimate and to later test that same estimate against Sionna RT's prediction.

Our example row (index 11491) gets its own random draw as part of this process. Whichever side of 0.6 that specific draw lands on determines its fate — we'll reveal which, for this exact row, at the end of this document.

7Step 5 — the minimum-per-side gate

if len(localization_rows) < 5 or len(validation_rows) < 5:
    n_towers_insufficient += 1
    continue

Even after passing the 20-row floor in Step 3, a cell could theoretically still end up with too few rows on one side of the split by bad luck (more likely for cells close to the 20-row minimum). If either side ends up with fewer than 5 rows, the whole cell is discarded here too — the same "insufficient data" outcome as Step 3, just caught one step later. For our example cell, with ~3,000 rows expected on the localization side and ~2,000 on the validation side, this is never remotely close to being triggered.

8Step 6 — computing the tower position (WCL)

Only the localization_rows — never the validation rows — are used here. This is the actual Weighted Centroid Localization calculation:

lat = localization_rows["Latitude"].values
lon = localization_rows["Longitude"].values
rsrp = localization_rows["PCell_RSRP_max"].values

weights = 10 ** (rsrp / 10.0)

est_lat = np.sum(weights * lat) / np.sum(weights)
est_lon = np.sum(weights * lon) / np.sum(weights)

To make the arithmetic concrete, here's a tiny worked example with just three fixes (a real cell's actual localization set has thousands, but the formula is identical):

FixLatitudeLongitudeRSRP (dBm)Weight = 10^(RSRP/10)
A52.493013.3010-800.00000001
B52.494513.3040-950.0000000003
C52.496013.3070-1050.00000000003

Fix A's weight is roughly 33× larger than Fix B's and about 316× larger than Fix C's (each 10 dB of RSRP difference is a 10× change in linear weight). When I compute Σ(weight×lat) / Σ(weight), Fix A — the strongest signal — pulls the estimated position much closer to its own coordinates than B or C do, even though all three fixes contribute something. That's the entire mechanism: strong-signal fixes dominate the average, weak-signal fixes barely nudge it.

For our real example cell, this calculation runs over all ~3,000 localization-side rows at once, producing a single (est_lat, est_lon) pair — the tower's estimated position.

9Step 7 — the spread diagnostic

distances = haversine_m(lat, lon, est_lat, est_lon)
weighted_spread_m = np.sum(weights * distances) / np.sum(weights)

Using the same weights from Step 6, this computes the weighted-average distance of every localization fix from the estimate that was just built from those same fixes. It's not a measure of accuracy against ground truth (we don't have any) — it's a measure of how spread out the contributing evidence was. In the real run, this cell's actual value came out to roughly 30-35 metres, in line with the typical result across the dataset.

10Step 8 — the consistency check

if len(distances) >= 5 and np.std(distances) > 1.0:
    correlation = np.corrcoef(distances, rsrp)[0, 1]
else:
    correlation = np.nan

if np.isnan(correlation):
    position_confidence = "unknown"
elif correlation < CONSISTENCY_CORRELATION_THRESHOLD:  # -0.1
    position_confidence = "high"
else:
    position_confidence = "low"

The problem this check is actually solving

We just estimated where a tower is using math (Step 6's weighted centroid). But here's the uncomfortable question: how do we know the estimate is actually right? Normally i'd check a guess like this against a map, a satellite photo, or an official record. We don't have that here — nobody handed us the real coordinates. So instead of checking "is this the right answer," this step checks something weaker but still useful: "does this answer behave the way a correct answer should behave?" It's a plausibility test, not proof.

The intuition — think of a campfire, not a tower

Imagine standing at different spots around a campfire at night, and someone asks me to guess where the fire is just from how warm it feel. I'd reason: wherever i feel warmest, the fire is probably closest to there; wherever i feel coldest, i're probably far from it. If i then guessed a location for the fire, a natural gut-check would be: as I move farther from my guessed spot, do I actually feel colder? If yes our guess passes the smell test. If someone standing far from my guess reports feeling hotter than someone standing close to it, something's wrong with our guess.

Cell towers work the same way with radio signal instead of heat. Signal strength (RSRP) is the "warmth." Our WCL estimate is the "guessed campfire location." This check asks exactly that gut-check question: as we move farther from our estimated tower position, does the measured signal actually get weaker?

Turning the gut-check into an actual number: correlation

np.corrcoef(distances, rsrp)[0, 1] computes a correlation — a single number between -1 and +1 that tells us whether two quantities move together or move opposite to each other, across every fix connected to this tower:

Correlation valueWhat it would mean
−1Perfectly opposite: every time distance goes up, RSRP goes down, with zero exceptions. The "textbook correct" pattern.
0No relationship at all: distance tells us nothing about signal strength. This would be suspicious — it's what I'd expect from random, meaningless data.
+1Perfectly together: farther away means stronger signal. Physically backwards — a red flag.

Across the real towers in this dataset, the typical result comes out around −0.7 to −0.8 — strongly negative, meaning "farther away really does mean weaker signal, clearly and consistently." That's a good sign the estimated position is roughly in the right neighborhood.

Why the cutoff is −0.1, and not 0 or −0.5

I might expect "any negative number should pass." But real-world data is noisy — buildings block signal unevenly, some spots have interference, GPS has small errors — so even a correct tower position won't produce a perfect −1; there will be scatter. CONSISTENCY_CORRELATION_THRESHOLD = -0.1 is deliberately lenient: it only rejects towers where the relationship is basically flat or has flipped backwards — not towers with a real, if imperfect, negative trend. It's "we're not demanding a clean signal, we're just checking the trend isn't broken or reversed."

What the three possible outcomes actually mean

OutcomeIn plain terms
position_confidence = "high"The data behaves the way it should if this tower is roughly where we say it is. Trust this estimate.
position_confidence = "low"Something's off — maybe too few fixes to see a clear trend, maybe the fixes all came from a cramped area that doesn't reveal direction well (like everyone standing on one side of the campfire), or maybe there's a real data quality issue with this specific tower. We don't know exactly which — we only know the estimate failed its own sanity check, so it's flagged rather than trusted blindly.
position_confidence = "unknown"We couldn't even run the test — too few fixes, or all the fixes sat at nearly the same distance from the estimate (like everyone standing shoulder-to-shoulder near the campfire — I learn nothing about "farther vs. closer" if nobody actually was farther or closer).

Back to our example row

This checks something we haven't checked yet: does the estimate make physical sense? If the estimated position is roughly correct, fixes taken farther from it should show weaker signal — so distance-from-estimate and RSRP should be negatively correlated. This cell (one of the "high confidence" towers in the real run) shows a strongly negative correlation, comfortably past the −0.1 threshold — the physical expectation holds up, which is the best evidence available, in the absence of any external ground truth, that this specific estimate is trustworthy.

Why this matters for what comes next 22 out of 267 towers (about 8%) in the real run came back "low confidence." They weren't thrown out — they were kept, but labeled — so that later, when these tower positions get used to test Sionna RT's ray-tracing predictions, it's possible to be extra skeptical of results tied to a low-confidence tower, or exclude them from the most important comparisons. It's the difference between silently trusting every estimate equally and actually knowing which ones to double-check.

11Step 9 — tagging every row and saving the outputs

df.loc[localization_rows.index, "tower_estimate_group"] = "localization"
df.loc[validation_rows.index, "tower_estimate_group"] = "validation"

This is the step that writes each row's fate permanently back into the full dataset (not just the clean subset used for estimation) — every row starts the script tagged "excluded" by default, and only rows belonging to a successfully-estimated cell, on either side of the split, get overwritten with "localization" or "validation". Rows that failed Gate-1 cleanliness, or belonged to a cell with too little data, simply keep the default "excluded" tag forever.

Two files get written out: one CSV per operator listing every estimated tower's position, spread, correlation, and confidence flag; and one large CSV — the full original dataset plus this new tower_estimate_group column — that every later script in the pipeline reads from.

12What happened to our example row, specifically

Row 11491 belongs to cell (1, 262, 1, 1492, 26947072) — a cell with 5,083 rows, comfortably clearing every minimum-data gate in Steps 3 and 5, and landing in the "high confidence" category in Step 8. Its own individual outcome in Step 4's random split — whether it personally became one of the roughly 3,000 localization fixes that helped build the estimate, or one of the roughly 2,000 validation fixes held back to test Sionna RT against later — is decided by its own random draw from that cell's seeded generator, exactly as described in Step 4. Either way, this row is one of the 76,614 (if validation) or 115,204 (if localization) rows in the real run that ended up meaningfully used, rather than one of the 15,616 marked "excluded".
